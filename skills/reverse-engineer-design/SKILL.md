# リバースエンジニアリング設計書ジェネレーター

ソースコードを解析し、体系化されたシステム設計書を自動生成する。

## 概要

このスキルは、リポジトリのソースコードを包括的に分析し、以下を含むシステム設計書を `docs/design/` ディレクトリに自動生成する：

- **システム概要・アーキテクチャ**（技術スタック、全体構成図）
- **API/エンドポイント一覧**（リクエスト/レスポンス例付き）
- **データモデル**（ER図、テーブル定義）
- **機能別詳細ドキュメント**（画面・API・DBを包括的に記述）

すべてのドキュメントは日本語で記述し、図表にはMermaidダイアグラムを積極的に使用する。

## ワークフロー

以下の手順を**完全自動**で実行する。途中でユーザーに確認を取る必要はない。

### Phase 1: リポジトリスキャン

目的：プロジェクトの全体像を素早く把握する。

1. **プロジェクト設定ファイルを読む**
   - `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `pom.xml`, `build.gradle`, `Gemfile`, `composer.json` 等
   - これにより技術スタック、依存ライブラリ、フレームワークを特定する

2. **ディレクトリ構造を確認する**
   - プロジェクトルートからの主要ディレクトリ構成を把握する
   - `src/`, `app/`, `pages/`, `routes/`, `api/`, `models/`, `components/`, `views/`, `controllers/`, `services/` 等の構造パターンを認識する

3. **README・既存ドキュメントを読む**
   - `README.md` があれば読み、プロジェクトの目的・概要を把握する
   - 既存の設計ドキュメントがあれば参考にする

4. **エントリーポイントを特定する**
   - アプリケーションの起動ポイント（`main.py`, `app.py`, `index.ts`, `server.js` 等）を特定する
   - ルーティング定義ファイルを見つける

### Phase 2: 詳細分析

目的：各セクションのドキュメント生成に必要な情報を収集する。

1. **アーキテクチャ分析**
   - アプリケーションの種類を判定する（Webアプリ、API、CLI、ライブラリ等）
   - レイヤー構成を把握する（プレゼンテーション層、ビジネスロジック層、データアクセス層）
   - 主要なデザインパターンを認識する（MVC、Clean Architecture、DDD等）
   - 外部サービス連携を特定する

2. **ルーティング・エンドポイント分析**
   - すべてのAPIエンドポイントを洗い出す
   - 各エンドポイントの HTTP メソッド、パス、パラメータ、レスポンス形式を解析する
   - 認証・認可の仕組みを把握する
   - ミドルウェアの適用状況を確認する

3. **データモデル分析**
   - ORM定義、マイグレーションファイル、スキーマ定義を読む
   - テーブル間のリレーションを把握する
   - 主要なフィールドとその型・制約を記録する

4. **機能ドメイン分析**
   - コードの構造・ルーティング・モデルから主要な機能ドメインを特定する
   - 各ドメインに属する画面（ページ/コンポーネント）、API、DBテーブルを紐付ける
   - ドメイン間の依存関係を把握する

5. **フロントエンド分析**（該当する場合）
   - ページ/画面構成を把握する
   - 主要なコンポーネントツリーを理解する
   - 状態管理の方式を確認する
   - 画面遷移のフローを把握する

### Phase 3: ドキュメント生成

以下の順序で `docs/design/` 配下にドキュメントを生成する。既に `docs/` ディレクトリが存在する場合は `docs/design/` サブディレクトリに出力して既存ファイルと共存させる。

#### 生成するファイル一覧

| ファイル | 内容 |
|---------|------|
| `README.md` | 目次・プロジェクト概要・ドキュメントマップ |
| `system-overview.md` | システム概要・アーキテクチャ・技術スタック |
| `api-endpoints.md` | 全エンドポイント一覧（詳細仕様） |
| `data-model.md` | 全体ER図・テーブル定義 |
| `features/<domain>.md` | 機能ドメインごとの詳細ドキュメント |

#### 3-1. README.md（目次）

プロジェクトの概要と全ドキュメントへのリンクを含む目次ファイル。

```markdown
# [プロジェクト名] システム設計書

## プロジェクト概要
（プロジェクトの目的・概要を2-3文で）

## 技術スタック
（主要技術をリスト形式で）

## ドキュメントマップ
- [システム概要・アーキテクチャ](./system-overview.md)
- [APIエンドポイント一覧](./api-endpoints.md)
- [データモデル](./data-model.md)
- 機能詳細
  - [機能名1](./features/xxx.md)
  - [機能名2](./features/yyy.md)
```

#### 3-2. system-overview.md

以下を含むこと：

- **システム構成図**（Mermaid `graph` または `C4Context` を使用）
- **技術スタック一覧**（カテゴリ別テーブル：言語、フレームワーク、DB、インフラ等）
- **ディレクトリ構成**（主要ディレクトリの役割を説明したツリー図）
- **アーキテクチャパターン**（採用しているデザインパターンの説明）
- **外部サービス連携**（連携先とその目的）

**システム構成図の例：**
```
graph TB
    Client[クライアント] --> LB[ロードバランサー]
    LB --> API[APIサーバー]
    API --> DB[(データベース)]
    API --> Cache[(キャッシュ)]
    API --> Queue[メッセージキュー]
```

#### 3-3. api-endpoints.md

各エンドポイントについて以下を記述する：

- **概要テーブル**（全エンドポイントの一覧。メソッド、パス、説明、認証要否）
- **詳細仕様**（エンドポイントごとに以下を記載）：
  - HTTPメソッドとパス
  - 説明
  - パスパラメータ / クエリパラメータ / リクエストボディ
  - レスポンス形式（JSON例）
  - 認証・認可要件
  - エラーレスポンス

**エンドポイント詳細の記述例：**
```markdown
### POST /api/users

ユーザーを新規作成する。

**リクエストボディ:**
\`\`\`json
{
  "name": "田中太郎",
  "email": "tanaka@example.com",
  "password": "securepassword123"
}
\`\`\`

**レスポンス (201 Created):**
\`\`\`json
{
  "id": 1,
  "name": "田中太郎",
  "email": "tanaka@example.com",
  "created_at": "2024-01-01T00:00:00Z"
}
\`\`\`

**認証:** 不要
```

#### 3-4. data-model.md

以下を含むこと：

- **全体ER図**（Mermaid `erDiagram` を使用）
- **テーブル定義**（テーブルごとに以下を記載）：
  - テーブル名と説明
  - カラム一覧（名前、型、制約、説明）
  - インデックス情報
  - リレーション
- **主要なリレーションの説明**

**ER図の例：**
```
erDiagram
    User ||--o{ Order : "places"
    Order ||--|{ OrderItem : "contains"
    OrderItem }o--|| Product : "references"
```

#### 3-5. features/<domain>.md（機能別詳細）

分析で特定した機能ドメインごとに1ファイルを作成する。各ファイルには以下を含む：

- **機能概要**（この機能ドメインが何を担当するか）
- **画面/ページ一覧**（該当する場合）
  - 各画面の概要と主要コンポーネント
  - 画面遷移図（Mermaid `stateDiagram-v2` または `flowchart`）
- **関連APIエンドポイント**
  - この機能で使用するエンドポイントの一覧と概要（詳細は api-endpoints.md へリンク）
- **関連データモデル**
  - この機能で使用するテーブルの一覧と概要（詳細は data-model.md へリンク）
  - 機能固有のER図（該当テーブルのみ抽出）
- **主要な処理フロー**
  - ユーザー操作からDBアクセスまでの代表的な処理フローをシーケンス図で表現（Mermaid `sequenceDiagram`）
- **ビジネスルール・バリデーション**
  - この機能固有のビジネスルールや入力バリデーション

## Mermaid ダイアグラム ガイドライン

Mermaidダイアグラムは設計書の理解を大幅に助ける。以下の使い分けを推奨する：

| 用途 | ダイアグラム種類 | 記法 |
|------|-----------------|------|
| システム全体構成 | フローチャート | `graph TB` or `graph LR` |
| 画面遷移 | 状態遷移図 | `stateDiagram-v2` |
| 処理フロー | シーケンス図 | `sequenceDiagram` |
| ER図 | ER図 | `erDiagram` |
| クラス構成 | クラス図 | `classDiagram` |
| デプロイ構成 | フローチャート | `graph TB` |

ダイアグラム内のラベルは日本語で記述する。ノードIDは英語で記述する（Mermaidの安定性のため）。

**注意事項：**
- ダイアグラムが大きくなりすぎる場合は、ドメインごとに分割する
- 1つのダイアグラムに含めるノードは15個以内を目安にする
- 読みやすさを優先し、すべてのリレーションを1つの図に詰め込まない

## フレームワーク別の分析ポイント

分析対象のフレームワークに応じて、以下の点に注目する。詳細は `references/framework-guide.md` を参照。

| フレームワーク | ルーティング定義 | モデル定義 | 画面定義 |
|---------------|-----------------|-----------|---------|
| Next.js / Nuxt.js | `app/` or `pages/` ディレクトリ構造 | Prisma / Drizzle / API レスポンス型 | `app/` or `pages/` のコンポーネント |
| Django / Rails | `urls.py` / `routes.rb` | `models.py` / `app/models/` | `templates/` / `views/` |
| FastAPI / Express | ルーターファイル | SQLAlchemy / Mongoose モデル | N/A（API専用の場合） |
| Spring Boot | `@RequestMapping` アノテーション | `@Entity` アノテーション | Thymeleaf テンプレート |
| Laravel | `routes/` ディレクトリ | `app/Models/` | `resources/views/` |
| Flutter / React Native | ナビゲーション定義 | ローカルDB / APIクライアント | Screen / Page コンポーネント |

## 分析対象にAPIやフロントエンドが存在しない場合

すべてのリポジトリが Web アプリケーションとは限らない。対象に応じて柔軟に対応する：

- **CLIツール**: 画面一覧の代わりにコマンド一覧・サブコマンド体系を記述する
- **ライブラリ**: APIエンドポイントの代わりにパブリックAPI（公開関数/クラス）を記述する
- **バッチ処理**: 処理フロー・スケジュール定義・入出力を中心に記述する
- **インフラ（IaC）**: リソース構成図・環境別設定を中心に記述する

存在しないセクションは無理に作らない。代わりに、そのリポジトリの本質に合ったセクションを設ける。

## 品質チェックリスト

ドキュメント生成後、以下を確認する：

- [ ] README.md の目次リンクがすべて正しいファイルを指している
- [ ] Mermaid ダイアグラムの構文が正しい（```mermaid で囲まれている）
- [ ] API エンドポイントにリクエスト/レスポンスの JSON 例が含まれている
- [ ] ER図が主要なテーブルとリレーションを網羅している
- [ ] 各機能詳細ファイルに画面・API・DBの情報が揃っている
- [ ] ファイル間のクロスリファレンスリンクが正しい
- [ ] 日本語で統一されている（コード内の英語はそのまま残す）
