# Presentation Hearing (presentation-hearing)

html-presentation スキルの**上流工程**。html-presentation は「入力にない事実を創作しない」
原則で動くため、良いスライドには良い入力が要る。本スキルの役割は、ユーザの頭の中にしか
ない内容を**ヒアリングで引き出し、ユーザが承認した文言だけ**でプレゼン入力ドキュメント
(YAML)を組み立てることである。

内容の創作はしない。ただし、ユーザの発言を**言語化・構造化して「こういうことですか?」と
提示し、承認を得て確定する**のは本スキルの中心的な仕事である(承認された文言はユーザ入力
として扱ってよい)。

## 全体フロー

```
Stage 1  全体像ヒアリング(用途・聴衆・目的・結論)
   ↓
Stage 2  構成案の提示と合意(ページ一覧の叩き台 → 修正 → 確定)
   ↓
Stage 3  ページ内容の深堀り(数ページずつ質問 → 記録)
   ↓
Stage 4  YAML保存 → ユーザ確認 → html-presentation でスライド生成
```

各StageでAskUserQuestionツールが使える環境なら積極的に使う(1回最大4問、選択肢+
自由記述で答えやすい)。使えない環境ではテキストで質問し回答を待つ。1度に大量の質問を
浴びせず、**回答を反映した中間成果物を見せながら**進めるのがコツ。

## Stage 1: 全体像ヒアリング

最初に以下を確認する。会話に既に答えがあれば聞き直さない。

1. **資料の種類・用途** — 提案・企画書 / 調査・分析報告 / 社内報告・共有 / その他
2. **聴衆・提出先** — 誰が読むか。意思決定者か、実務者か、社外か
3. **目的(出口)** — 読んだ人にどうしてほしいか(承認・発注・理解・議論 等)
4. **キーメッセージ** — 一言でいうと何を伝える資料か(未定なら「未定」でよい。
   Stage 3 の材料が揃った後に候補を提示して決める)

あわせて **既にある素材**(データ・メモ・過去資料)と**ページ数の目安**を聞く。
素材ファイルの提供があれば読み込み、以降のヒアリングでは「素材にある内容の確認」に
質問を置き換える(あるものを聞き直さない)。

用途が決まったら `references/question-bank.md` を読み、その用途の質問セットを
Stage 2・3 の質問設計に使う。

## Stage 2: 構成案の提示と合意

Stage 1 の回答から**ページ一覧の叩き台**を作って提示する。形式:

| No | スライド型 | ページタイトル | このページで聞くこと |
|---|---|---|---|
| 1 | 表紙 | ○○提案書 | 提出先・作成者・日付 |
| 2 | 目的・背景 | 本提案の背景 | 現状の課題認識 |

- スライド型は html-presentation の `references/slide-patterns.md` の11パターン
  (下記「スライド型の値」参照)から選ぶ。判断に迷えば「おまかせ」とする
- ページ数の目安に収める。1ページに詰め込みすぎない(要点3〜5個/ページが上限)
- 提示したら**必ずユーザの修正・合意を得てから** Stage 3 に進む。ページの追加・削除・
  並べ替えの希望を聞く

## Stage 3: ページ内容の深堀り

確定した構成に沿って、**2〜4ページずつ**まとめて内容を質問する(表紙などヒアリング
不要のページは飛ばす)。質問のたびに:

- そのページの「聞くこと」を具体的な問いにする(question-bank参照)。
  抽象的な「内容を教えてください」ではなく、「比較対象は何社ですか」「効果は数値で
  言えますか」のようにスライドに書ける粒度で聞く
- 回答を**そのページのcontentとして文章化して見せ、確認を得る**。ユーザが「おまかせ」
  と言った箇所は、ドラフト文言を提示して承認を得る(承認前の文言をYAMLに入れない)
- 分からない・未定と言われた項目は無理に埋めない。省略するか、表紙の定型要素
  (提出先・作成者・日付)のみプレースホルダ「●●●」で残す
- 回答が想定より膨らんだらページ分割を、乏しければページ統合を提案する(構成は
  Stage 2 で固定ではなく、合意を取りながら更新してよい)

## Stage 4: YAML化・確認・スライド生成

1. 下記仕様のYAMLを組み立て、作業ディレクトリに `<資料名スラッグ>.presentation.yaml`
   として保存する
2. ユーザに**ページごとのタイトルと内容の要約**を提示し、修正がないか最終確認する
3. OKが出たら html-presentation スキルを呼び出し、このYAMLを入力としてスライドを
   生成する(YAMLの `pattern` はスライド型の指定として、`content` は入力原稿として
   そのまま渡る。html-presentation は `references/input-format.md` の契約で読む)。
   html-presentation 側の確認(マッピング提示)は済んでいる内容なので
   「一気通貫で生成してよい」と明示する。Skillツールで呼び出せない環境では
   html-presentation の SKILL.md を読み、その手順に従って自分で生成する

## 出力YAML仕様

出力形式は `html-presentation/references/input-format.md` の契約に準拠する。

```yaml
title: 地域中小企業のDX推進実態調査 報告書
meta:
  audience: 経済産業省 御中
  author: ○○総合研究所
  date: 2026年7月
purpose: 調査結果を報告し、次年度施策の方向性について合意を得る
key_message: DX停滞の主因は人材不足であり、伴走支援型の施策が必要
pages:
  - no: 1
    pattern: 表紙
    title: 地域中小企業のDX推進実態調査 報告書
    content: |
      副題: 令和8年度○○委託事業
  - no: 2
    pattern: 目的・背景
    title: 調査の背景と目的
    message: 補助金施策にもかかわらず中小企業のDXは停滞している
    content: |
      背景: 補助金施策にもかかわらず中小企業のDXは停滞している。
      目的: 停滞要因の構造把握と次年度施策の立案。
    source: 令和7年度○○調査
```

- `pages[].no` / `title` / `content` / `pattern` は必須。`content` はそのページに
  載せる内容の文章・箇条書き(ブロックスカラー `|` で複数行)。ヒアリングで確認の
  取れた文言のみを書く
- `chapter`(章扉/上部ラベル)/ `message`(キーメッセージ行)/ `source`(出典)は任意。
  ヒアリングで確認が取れた場合のみ付ける(無ければ省略。創作しない)
- `meta` の3要素は表紙用。未確認なら値を `●●●` にする
- `purpose` / `key_message` はスライドに直接載らなくてもよい。html-presentation が
  トーンや強調(`<strong>`)を判断する材料になる
- `pattern` の値は下記「スライド型(pattern)の値」= input-format.md の正典キーを使う

### スライド型(pattern)の値

`表紙` `目的・背景` `タスク分解` `矢羽スケジュール` `論点整理` `スコープ定義`
`分析サマリー` `分析詳細` `2軸マトリックス` `課題整理` `対応表・考察` `おまかせ`

これらは html-presentation の `references/input-format.md` の**正典キー**であり、各型の
中身は同スキルの `references/slide-patterns.md` を参照。

各型が何かは html-presentation の `references/slide-patterns.md` を参照。ヒアリング中に
型を決めるのは「そのページで何を聞くべきか」を明確にするため(例: 矢羽スケジュール
なら期間・工程・節目を聞かねばならない)。

## ヒアリングの心得

- **創作と言語化の線引き**: ユーザが言っていない事実・数値を足すのは創作(禁止)。
  ユーザの発言を整理して見せ、承認を得るのは言語化(推奨)
- **質問は答えやすく**: 選択肢を添える。「一般的にはA案が多いですがどうしますか」の
  ように相場観を提供してよい(それ自体は事実の創作ではない)
- **進捗を見せる**: Stage 2 の構成表、Stage 3 の確認文のように、回答が形になっていく
  のを見せるとユーザは答え続けやすい
- **切り上げどき**: ユーザが「あとはおまかせ」「もう作って」と言ったら、未確定項目を
  ドラフト提示 → 一括承認に切り替えて Stage 4 へ進む。ヒアリングを引き延ばさない
