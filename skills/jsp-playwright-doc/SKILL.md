# JSP → Playwrightページオブジェクト ドキュメント生成

入力ディレクトリ配下の各JSPを1画面として解析し、Playwrightのページオブジェクト(1画面=1クラス)を実装するために必要な情報をMarkdownドキュメントとして生成する。

## 概要

ゴールは「そのMarkdownを見れば、迷わずページオブジェクトが書ける」状態を作ること。各画面について次の3つを揃える。

1. **操作可能な要素のロケーター情報** — 推奨ロケーター1つと、他の候補を併記する。テキストや画像など操作できない要素は対象外(必要なら後から個別追加)。
2. **想定オペレーション** — 「フォームに入力してsubmitする」「リンクをクリックする」といった操作に**日本語の名前**を付けて手順を記述する。ページオブジェクトのメソッドの元になる。
3. **内部遷移先** — オペレーションの結果どの画面に遷移するか。外部アクセス(別ホストへの絶対URL等)は対象外とし、システム内部の遷移のみを扱う。

出力は `./output` ディレクトリに、入力ディレクトリと**同じ階層構成**でMarkdownを配置する(例: `input/user/login.jsp` → `output/user/login.md`)。

## 重要な前提

- **入力エンコーディングはMS932(CP932 / Windows-31J / Shift_JIS上位互換)**。UTF-8として読むと文字化けするため、必ずCP932でデコードすること。
- **1ファイルにつき1サブエージェントを呼び出す**。各サブエージェントが1つのJSPを解析し、対応するMarkdownを1枚書き上げる。画面単位で情報が閉じるため、ページオブジェクト(1画面1クラス)の粒度と一致する。
- **includeは追わない**。`<%@ include %>` / `<jsp:include>` で取り込む共通部品(ヘッダー/フッター等)は、「取り込んでいる」という事実とパスだけを記録し、中身は解析しない(別途個別対応)。

## ワークフロー

途中でユーザーに逐一確認する必要はない。入力ディレクトリが不明な場合のみ確認する。

### Phase 1: 対象JSPの列挙

1. 入力ディレクトリ(ユーザー指定。既定は `input`)配下の `*.jsp` を再帰的に列挙する。
   ```bash
   find <入力ディレクトリ> -type f -name '*.jsp' | sort
   ```
2. 出力ルート `./output` を作成する。各JSPの相対パスから出力先 `.md` パスを決める(拡張子を `.md` に置換)。
3. 対象が0件なら、その旨を伝えて終了する。

### Phase 2: ファイルごとにサブエージェントで解析(並列)

各JSPに対して1つずつサブエージェントを起動する(独立作業なので同一ターンで複数起動して並列化してよい。大量の場合は10前後ずつバッチ実行する)。

**必ず専用エージェント `jsp-playwright-doc-analyzer` を使う**(Agentツールの `subagent_type`、Workflowなら `agentType` に指定)。このエージェントはJSP解析とロケーター/オペレーション抽出に特化しており、限界まで詳細に解析する手順を内蔵している。何らかの理由で専用エージェントが使えない場合のみ汎用エージェントにフォールバックし、その際は下記プロンプトに加えて `references/analysis-guide.md` を必ず読ませること。

`jsp-playwright-doc-analyzer` へ渡す情報は最低限これだけ:

```
このタスクを実行してください。
- 解析対象JSP(絶対パス): <input>/xxx/yyy.jsp
- 出力先Markdown(絶対パス): <output>/xxx/yyy.md
- 入力エンコーディング: MS932 (CP932)
- Markdownテンプレート: <skill>/references/analysis-guide.md を必ず読んで、その4セクション・全列を厳守すること
- 完了したら、出力したファイルパスと「要素数・オペレーション数・特記事項」を数行で報告すること
```

サブエージェントの成果物はMarkdownファイルそのもの。返り値には要約(何を出力したか)だけを求め、本文は求めない(コンテキスト節約)。

### Phase 3: 集約と報告

1. 全サブエージェント完了後、`output` 配下に生成されたMarkdown一覧を確認する。
2. 生成できなかった/情報が薄いファイルがあれば列挙する。
3. ユーザーへ「生成ファイル数・対象画面一覧・注意点(動的ロケーターやincludeで中身未解析の画面など)」を簡潔に報告する。

## サブエージェントを使う理由

JSPは画面ごとに独立しており、1画面=1ページオブジェクトの粒度と綺麗に一致する。ファイル単位でサブエージェントに閉じ込めることで、(a) 各画面の解析が他画面の文脈で汚染されない、(b) 大量ファイルでも並列で捌ける、(c) オーケストレーター側のコンテキストを要素ダンプで溢れさせない、という利点がある。

## 解析の要点(詳細は references/analysis-guide.md)

- **対象要素**: フォーム入力(input/textarea/select/checkbox/radio)、ボタン、submit、システム内部へのリンク、`onclick`等で内部遷移するクリック要素。**テキスト・画像など操作できない要素は取得しない**。
- **ロケーター**: `id` を最優先、次に `name`、次にrole/label/text、最後にCSS/相対XPath。推奨を1つ選び、他は候補として併記する。値がJSPで動的(`id="row_${item.id}"` 等)な場合は、その旨と想定パターンを注記する。
- **タグリブ対応**: Struts/Spring MVC/JSF等のタグ(`<html:text>` `<form:input>` 等)は生JSPのままロケーター化せず、**レンダリング後のHTML属性(id/name)を推定**して起こし、推定である旨を備考に残す。
- **オペレーション命名**: 画面文脈で意味の分かる日本語名を付ける(例:「ログイン」「検索実行」「新規登録画面へ遷移」)。手順は「どの要素をどう操作するか」を番号付きで書く。
- **要素↔遷移先の紐づけ**: 各オペレーションに、遷移を発火する**トリガー要素**(押すボタン/クリックするリンク)を独立フィールドで明記する。要素表には「関連オペレーション」列、遷移先表には「トリガー要素」列を持たせ、どの要素を操作するとどこへ遷移するかを構造で一意にする。**1フォームに複数の遷移先(`formaction` やサーバ側の値分岐)がある場合は、遷移先ごとに別オペレーションへ分割**する。
- **内部/外部の判定**: 相対パスや自アプリ配下(`.jsp` `.do` `.action` 等)は内部。`http(s)://別ホスト`・`mailto:`・`tel:`・別ドメインへの絶対URLは外部として除外する。

## よくある失敗

| 失敗 | 対策 |
|---|---|
| UTF-8で読んで文字化け | 必ずCP932でデコード(`open(path, encoding='cp932')` 等) |
| 出力構成が入力とズレる | 入力からの相対パスを保ち、拡張子だけ`.md`に |
| テキスト/画像まで要素化 | 操作可能な要素のみ対象。装飾は取得しない |
| 外部リンクを遷移先に含める | 別ホスト絶対URL等は除外。内部遷移のみ |
| includeの中身まで解析 | includeはパス記録のみ。中身は追わない |
| 動的属性を固定値のロケーターにする | 動的な箇所はパターンとして注記する |
| タグリブのタグをそのままロケーター化 | レンダリング後のid/nameを推定し、推定と注記する |
| 要素と遷移先が名前一致でしか繋がっていない | オペレーションに「トリガー要素」を明記し、遷移先表もトリガー要素で紐づける |
| 1フォーム複数遷移先を1操作にまとめて曖昧化 | ボタン(`formaction`/送信値)ごとに別オペレーションへ分割する |
