# JSP解析ガイド(サブエージェント用)

あなたは1つのJSPファイルを解析し、Playwrightのページオブジェクト(1画面1クラス)を書くためのMarkdownを1枚生成する。以下の手順とテンプレートに厳密に従うこと。

## 0. 入力の読み込み(MS932)

入力JSPは **MS932(CP932 / Windows-31J)** でエンコードされている。UTF-8で読むと文字化けするので必ずCP932でデコードする。

```python
from pathlib import Path
text = Path(jsp_path).read_text(encoding="cp932", errors="replace")
```

（コマンド派なら `iconv -f CP932 -t UTF-8 input.jsp`。ただしPythonのcp932が最も無難。）

デコードした本文を対象に解析する。以降「HTML」と言うときは、JSPが出力するであろうHTMLタグを指す。

## 1. 解析対象と対象外

**対象(操作可能な要素のみ)**:
- フォーム部品: `<input>`(text/password/email/number/hidden以外の操作可能なもの/checkbox/radio/file/submit/button/reset)、`<textarea>`、`<select>`、`<button>`
- システム内部へのリンク: `<a href="...">` のうち内部遷移するもの
- クリックで内部遷移する要素: `onclick` 等で画面遷移する `<a>`/`<button>`/`<div>` など

**対象外(取得しない)**:
- 表示のみのテキスト、ラベル文言、見出し、`<img>` などの画像、装飾要素
- 外部アクセスのリンク(下記「内部/外部判定」参照)
- `type="hidden"` の入力(ロケーター表には載せない。ただしフォームsubmit時に送られる重要パラメータがあればオペレーションの備考に一言触れてよい)

操作できない要素は「必要に応じて後から個別追加」する前提なので、無理に列挙しない。

## 2. 内部/外部リンクの判定

| 種類 | 判定 |
|---|---|
| 相対パス(`foo.jsp`, `./x`, `../x`, `sub/x.do`) | 内部 |
| 自アプリ配下の絶対パス(`/app/x.jsp`, `/x.do`, `/x.action`) | 内部 |
| `http://` `https://` で**別ホスト**を指す | 外部 → 除外 |
| `mailto:` `tel:` `javascript:void(0)`(遷移なし) | 対象外 |
| `javascript:` だが実質内部画面へ遷移 | 内部として扱い、遷移先を推定 |

外部リンクはオペレーションにも遷移先にも含めない。

## 3. ロケーター情報の作り方(推奨1つ+候補)

各要素について、Playwrightで安定して掴むための情報を集める。優先順位:

1. `id` 属性 → 最優先(`#id` / `getByTestId`相当)
2. `name` 属性 → フォーム部品で有効
3. role + アクセシブルネーム / ラベル(`getByRole`, `getByLabel`)、リンク・ボタンの表示テキスト(`getByText`, `getByRole('link', {name})`)
4. CSS セレクタ / 相対XPath(最後の手段)

**推奨ロケーター**を1つ選び、他に使えるものを**候補**として併記する。属性値がJSPで動的に生成される場合(例 `id="row_${item.id}"`, `name="items[0].qty"`)は、固定値にせず**パターンと注記**を残す(例:「id は動的。前方一致 `[id^="row_"]` か行インデックス指定が必要」)。

## 4. オペレーションの洗い出し

その画面で想定される操作に**日本語の名前**を付ける。代表的な型:

- **フォーム入力+submit**: 入力欄に値を入れて送信ボタンを押す一連。例「ログイン」「検索実行」「登録」。
- **リンククリック / ボタン遷移**: 内部画面へ移動する操作。例「新規登録画面へ遷移」「一覧へ戻る」。

各オペレーションには次を必ず書く。ページオブジェクトのメソッド ↔ 触る要素 ↔ 遷移先が構造として一意に辿れるようにするのが目的。

- **種別**: フォーム入力+submit / リンククリック / ボタン遷移 など
- **トリガー要素**: その遷移を**実際に発火させる1つの要素**(押されるボタン/クリックされるリンク)を論理名+ロケーターで明記する。オペレーションと遷移先はこの要素で紐づく。
- **入力要素**: submit前に値を入れる要素の論理名(あれば。無ければ「なし」)
- **手順**: 番号付きで、どの要素をどう操作するか(論理名で参照)
- **遷移先**: 分かる範囲で内部URL / JSP名

**なぜトリガー要素を独立させるか**: 「どの要素を操作するとどこへ遷移するか」を名前の一致に頼らず構造で固定するため。オペレーション名が汎用的・重複していても、トリガー要素(ロケーター)が遷移先を一意に決める。

### 同一フォームに複数の遷移先がある場合(重要)

1つの `<form>` でも、押すボタンによって遷移先が変わることがある。曖昧さの温床なので、**遷移先ごとに別オペレーションへ分割**し、それぞれにトリガー要素を割り当てる。判定材料:

- **`formaction` 属性**: そのボタンは form の `action` を上書きして別URLへ送信する(ボタンごとに遷移先が違う決定的な根拠)。
- **同じ action でサーバ側分岐**: `<button name="mode" value="confirm">`/`value="save">` のように、送信パラメータ(name/value)でサーバ側が遷移先を振り分けるパターン。値をトリガー要素の備考に残し、遷移先が「同一URLだが送信値で分岐」である旨を明記する(遷移先JSPは推定になる)。
- **複数の `<form>`**: フォームごとにsubmitオペレーションを分ける。

いずれの場合も、共有する入力要素(商品名・数量など)は各オペレーションの「入力要素」に併記し、要素表の「関連オペレーション」で全オペレーションを指すようにする。

## 5. Markdownテンプレート(この構成を厳守)

```markdown
# <画面名> (<入力からの相対パス>)

## 画面概要
- 目的: <この画面が何をする画面か 1〜3行>
- URL/マッピング: <分かる範囲で。form action や JSP パスなど。不明なら「不明」>
- include: <取り込んでいる共通部品のパス一覧。中身は未解析。無ければ「なし」>

## 要素(ロケーター)
| 論理名 | 種別 | 推奨ロケーター | 候補ロケーター | 関連オペレーション | 備考 |
|---|---|---|---|---|---|
| ユーザーID | text入力 | `#userId` (id=userId) | `name=userId` / `getByLabel("ユーザーID")` | ログイン | 必須 |
| パスワード | password入力 | `#password` | `name=password` | ログイン | 必須 |
| ログイン | ボタン(submit) | `getByRole("button", name="ログイン")` | `#loginBtn` | ログイン ★トリガー | フォーム送信 |
| 新規登録 | リンク | `getByRole("link", name="新規登録")` | `a[href="register.jsp"]` | 新規登録画面へ遷移 ★トリガー | 内部遷移 |

## オペレーション
### ログイン
- 種別: フォーム入力+submit
- トリガー要素: 「ログイン」ボタン (`#loginBtn`)
- 入力要素: ユーザーID, パスワード
- 手順:
  1. 「ユーザーID」に値を入力
  2. 「パスワード」に値を入力
  3. 「ログイン」ボタン(`#loginBtn`)を押下
- 遷移先: /main (menu.jsp) ※内部

### 新規登録画面へ遷移
- 種別: リンククリック
- トリガー要素: 「新規登録」リンク (`getByRole("link", name="新規登録")`)
- 入力要素: なし
- 手順:
  1. 「新規登録」リンクを押下
- 遷移先: /register (register.jsp) ※内部

## 遷移先
| オペレーション | トリガー要素 | 遷移先URL | 遷移先JSP | 種別 |
|---|---|---|---|---|
| ログイン | 「ログイン」ボタン (`#loginBtn`) | /main | menu.jsp | 内部 |
| 新規登録画面へ遷移 | 「新規登録」リンク | /register | register.jsp | 内部 |
```

**同一フォーム複数遷移先の記入例**（1フォームに `formaction` 違いのボタンが3つ）:

```markdown
## 遷移先
| オペレーション | トリガー要素 | 遷移先URL | 遷移先JSP | 種別 |
|---|---|---|---|---|
| 確認画面へ | 「確認画面へ」ボタン (`#confirmBtn`) | /app/order/confirm.do | confirm.jsp(推定) | 内部 |
| 下書き保存 | 「下書き保存」ボタン (`#draftBtn`, formaction) | /app/order/saveDraft.do | saveDraft.jsp(推定) | 内部 |
| キャンセル | 「キャンセル」ボタン (`#cancelBtn`, formaction) | /app/order/list.do | list.jsp(推定) | 内部 |
```
同じ入力要素(商品名・数量)を持つ3操作だが、**トリガー要素(押すボタン)で遷移先が一意に決まる**ことが表から読み取れる。

### テンプレート運用ルール
- セクションは常に4つ(画面概要 / 要素(ロケーター) / オペレーション / 遷移先)。該当なしなら表の行を空にせず「(なし)」と1行書く。
- 「論理名」は日本語のラベルや周辺文言から人間が読んで分かる名前を付ける(ラベルが無ければ `name`/`id` から推測し、推測である旨を備考に書く)。
- 要素表の「論理名」とオペレーションの各フィールド(トリガー要素/入力要素/手順)で参照する名前を一致させる(ページオブジェクトのフィールド↔メソッドの対応になる)。
- **要素↔遷移先は必ず「トリガー要素」で紐づける**。要素表の「関連オペレーション」列には、その要素が関与する全オペレーション名を書き、遷移を発火する要素には `★トリガー` を付ける。遷移先表は各行にトリガー要素を書き、遷移先が「どの要素を操作した結果か」を一意に示す。
- 遷移先はオペレーション名の一致に頼らない。名前が汎用的でも、トリガー要素のロケーターで遷移先が特定できる状態にする。
- 動的ロケーターや判断に迷った点は「備考」や注記に必ず残す。空欄で誤魔化さない。

## 6. 出力

上記Markdownを指定された出力先パスに **UTF-8** で書き出す(出力はUTF-8。入力のCP932と混同しないこと)。出力ディレクトリが無ければ作成する。
